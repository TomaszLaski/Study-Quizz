Część I — Baza B1–B3
B1  Debounce  „zaczekaj aż user przestanie coś robić”
CO ROBI
Opóźnia akcję aż minie X ms od ostatniej zmiany. Każda nowa zmiana resetuje licznik.
MECHANIZM
setTimeout ustawia akcję na później; clearTimeout w cleanup kasuje poprzedni timer, zanim ustawi
nowy.
KIEDY
Search-as-you-type, auto-save, obsługa resize. Wszędzie gdzie „po ostatniej zmianie, nie po każdej”.
Debounce nie powinien wiedzieć, co debounce'uje — stąd generyk.
GDZIE GO UŻYJESZ
A1 (query do wyszukiwarki), A2 (cisza przed zapisem), A7 (filtr tekstowy tabeli).
TYPOWA FORMA
function useDebouncedValue<T>(value: T, delay: number): T {
  const [debounced, setDebounced] = useState(value)
  useEffect(() => {
    const id: ReturnType<typeof setTimeout> = setTimeout(
      () => setDebounced(value),
      delay
    )
    return () => clearTimeout(id)   // nowa zmiana kasuje poprzedni timer
  }, [value, delay])
  return debounced
}
PUŁAPKI
!  Cleanup timera w return useEffect — inaczej timer odpala po unmount
 
!  Typ timera: ReturnType<typeof setTimeout> (Node i przeglądarka różnią się)
 
!  Nie mylić z throttle — throttle przepuszcza co X ms, debounce czeka na ciszę

B2  Async fetcher z 4 stanami  idle / loading / success / error (+ empty)
CO ROBI
Pobiera dane i modeluje wszystkie możliwe stany operacji. Każdy fetch ma dokładnie jeden aktywny
stan.
MECHANIZM
useReducer lub kilka useState + fetch w useEffect. Stany jako discriminated union eliminują
nielegalne kombinacje (loading + error naraz).
KIEDY
Każde pobieranie danych z API. To najczęstszy klocek w ogóle.
GDZIE GO UŻYJESZ
Wszystkie A1–A10 — każdy fetch w bibliotece to B2 w jakiejś odmianie (akumulacja w A3, progress w
A9, tick w A10).
TYPOWA FORMA
type State<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T[] }
  | { status: 'empty' }
  | { status: 'error'; message: string }
type Action<T> =
  | { type: 'FETCH_START' }
  | { type: 'FETCH_SUCCESS'; data: T[] }
  | { type: 'FETCH_ERROR'; message: string }
function reducer<T>(state: State<T>, action: Action<T>): State<T> {
  switch (action.type) {
    case 'FETCH_START':
      return { status: 'loading' }
    case 'FETCH_SUCCESS':
      return action.data.length === 0
        ? { status: 'empty' }
        : { status: 'success', data: action.data }
    case 'FETCH_ERROR':
      return { status: 'error', message: action.message }
  }
}
PUŁAPKI
!  fetch NIE rzuca dla 4xx/5xx — sprawdź res.ok ręcznie
 
!  Stan empty ≠ error — pusta lista to poprawny wynik, nie błąd
 
!  Stan idle na starcie — rozróżnij „jeszcze nie szukano” od „szukano, pusto”
 
B3  Cleanup / anulowanie  sprzątanie żywych operacji
CO ROBI
Każda żywa operacja — timer, fetch, event listener, subskrypcja — musi być zatrzymana, gdy
komponent znika lub gdy zależność efektu się zmienia.
MECHANIZM
Funkcja return () => {...} w useEffect. Dla fetch: AbortController + controller.abort() w
cleanup.
KIEDY
Zawsze gdy w efekcie startujesz cokolwiek, co „żyje” dłużej niż render. To nie opcja — to obowiązek.
GDZIE GO UŻYJESZ
Wszystkie A1–A10. Odmiany: abort fetchu (A1/A4/A8/A10), clearTimeout (B1), removeEventListener
(B7), xhr.abort() (A9).

TYPOWA FORMA
useEffect(() => {
  const controller = new AbortController()
  fetch(url, { signal: controller.signal })
    .then(res => {
      if (!res.ok) throw new Error(`HTTP ${res.status}`)
      return res.json()
    })
    .catch(err => {
      if (err.name === 'AbortError') return   // intencja, nie błąd
      // realny błąd
    })
  return () => controller.abort()
}, [url])
PUŁAPKI
!  AbortError w catch to NIE błąd — ignoruj go, to twoja intencja
 
!  Event listener — ta sama referencja funkcji do add i removeEventListener
 
!  React StrictMode montuje 2x w devie — cleanup musi być poprawny
 
Część II — Fala 2: B4–B7
B4  Retry z backoffem  „spróbuj jeszcze raz, ale mądrze”
CO ROBI
Ponawia nieudane żądanie ograniczoną liczbę razy, z rosnącym odstępem między próbami. Użytkownik
dostaje wynik mimo chwilowej czkawki sieci.
MECHANIZM
Pętla prób: po porażce czekaj delay · 2^attempt ms i próbuj ponownie, aż do limitu. Retry tylko dla
błędów przejściowych (sieć, 5xx) — nigdy dla 4xx i nigdy dla AbortError.
KIEDY
Dociąganie porcji w infinite scroll, upload, polling. Wszędzie, gdzie porażka bywa chwilowa, a
ponowienie jest bezpieczne (GET / idempotentne).
GDZIE GO UŻYJESZ
A3 (retry porcji — przycisk „Spróbuj ponownie” to ręczna wersja B4), A9 (retry uploadu), A10
(przejściowy błąd ticka).

TYPOWA FORMA
async function fetchWithRetry(
  url: string,
  init: RequestInit = {},
  retries = 3,
  baseDelay = 500
): Promise<Response> {
  for (let attempt = 0; ; attempt++) {
    try {
      const res = await fetch(url, init)
      // 4xx: błąd klienta - retry nic nie da, oddaj od razu
      if (res.ok || res.status < 500) return res
      if (attempt === retries) return res      // 5xx, próby wyczerpane
    } catch (err) {
      if ((err as Error).name === 'AbortError') throw err  // intencja
      if (attempt === retries) throw err       // realny błąd, koniec prób
    }
    const jitter = Math.random() * 100
    await new Promise(r => setTimeout(r, baseDelay * 2 ** attempt + jitter))
  }
}
PUŁAPKI
!  Nie ponawiaj 4xx — błąd klienta nie zniknie po trzeciej próbie, tylko potroisz ruch
 
!  AbortError przerywa NATYCHMIAST — anulowanie to intencja usera, nie awaria do naprawienia
 
!  Limit prób obowiązkowy — retry bez limitu to pętla DDoS na własne API
 
!  Jitter (losowy dodatek) — bez niego tysiąc klientów ponawia w tej samej milisekundzie
 
!  POST bez idempotencji = ryzyko podwójnego zapisu — retry tylko tam, gdzie ponowienie bezpieczne
 
B5  Cache + deduplikacja żądań  ręcznie napisany rdzeń React Query
CO ROBI
Ten sam klucz zapytania = jeden fetch. Trwający request jest współdzielony (dedup), zakończony —
zapamiętany (cache). Kolejni pytający dostają wynik bez dotykania sieci.
MECHANIZM
Dwie mapy: cache (klucz → dane) i inflight (klucz → Promise). Kolejność sprawdzania: cache → inflight
→ dopiero fetch. Promise ląduje w inflight od razu, znika w finally, wynik wpada do cache. Mutacja
inwaliduje klucz.
KIEDY
Dwa komponenty pytają o to samo; powrót do odwiedzonej strony tabeli; podpowiedzi w search dla
powtórzonego query.
GDZIE GO UŻYJESZ
A1 (powtórzone query), A7 (odwiedzone strony tabeli). Narracja senioralna: tak działa queryKey i dedup
w React Query.

TYPOWA FORMA
const cache = new Map<string, unknown>()
const inflight = new Map<string, Promise<unknown>>()
export function fetchOnce<T>(key: string, fetcher: () => Promise<T>): Promise<T> {
  if (cache.has(key)) return Promise.resolve(cache.get(key) as T)
  const pending = inflight.get(key)
  if (pending) return pending as Promise<T>   // dedup: dołącz się do trwającego
  const p = fetcher()
    .then(data => { cache.set(key, data); return data })
    .finally(() => inflight.delete(key))      // sukces CZY porażka: zwolnij slot
  inflight.set(key, p)
  return p
}
export function invalidate(prefix: string) {
  for (const k of cache.keys()) if (k.startsWith(prefix)) cache.delete(k)
}
PUŁAPKI
!  Klucz = pełna tożsamość zapytania (endpoint + parametry), nie sam endpoint — inaczej strona 2
 dostaje dane strony 1
!  Inwalidacja po mutacji obowiązkowa — stale dane po zapisie są gorsze niż brak cache
 
!  inflight czyścisz w finally, nie w then — nieudany Promise w mapie blokuje ponowienie na zawsze
 
!  Cache w module = współdzielony między testami i requestami SSR — wiedz, że to trade-off
 
!  Nie cache'uj odpowiedzi błędnych — porażka nie jest wynikiem do współdzielenia
 
B6  useLocalStorage / persystencja  stan, który przeżywa refresh
CO ROBI
Stan Reacta lustrzany w localStorage: przeżywa odświeżenie strony, a przez zdarzenie storage
synchronizuje się między kartami przeglądarki.
MECHANIZM
Lazy initializer w useState czyta localStorage RAZ na starcie (w try/catch). Efekt pisze przy każdej
zmianie. Drugi efekt nasłuchuje storage — zdarzenie przychodzi tylko z INNYCH kart.
KIEDY
Szkic formularza/wizarda, preferencje tabeli, motyw, ostatnio oglądane. Nie dla sekretów —
localStorage czyta każdy skrypt na stronie (XSS).
GDZIE GO UŻYJESZ
A6 (szkic przeżywa refresh), A7 (zapamiętane filtry i rozmiar strony), motywy i preferencje w każdej
appce.

TYPOWA FORMA
function useLocalStorage<T>(key: string, initial: T) {
  const [value, setValue] = useState<T>(() => {
    try {
      const raw = localStorage.getItem(key)
      return raw !== null ? (JSON.parse(raw) as T) : initial
    } catch {
      return initial          // uszkodzony wpis nie wywala appki
    }
  })
  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value))
  }, [key, value])
  useEffect(() => {
    const onStorage = (e: StorageEvent) => {
      if (e.key === key && e.newValue !== null) {
        setValue(JSON.parse(e.newValue) as T)   // sync z INNEJ karty
      }
    }
    window.addEventListener('storage', onStorage)
    return () => window.removeEventListener('storage', onStorage)
  }, [key])
  return [value, setValue] as const
}
PUŁAPKI
!  JSON.parse zawsze w try/catch — jeden uszkodzony wpis nie może wywalić aplikacji
 
!  Lazy initializer (funkcja w useState) — czytasz localStorage raz, nie co render
 
!  storage odpala się tylko w INNYCH kartach — ta sama karta nie usłyszy własnego zapisu
 
!  SSR: localStorage nie istnieje na serwerze — guard typeof window przed dotknięciem
 
!  Sekrety i tokeny NIE tu — localStorage jest czytelny dla każdego skryptu (XSS)
 
B7  useEventListener  generyczne ucho na zdarzenia
CO ROBI
Jedno generyczne opakowanie na addEventListener z gwarantowanym sprzątaniem i pełnym
typowaniem zdarzenia z nazwy. Koniec z ręcznym pilnowaniem par add/remove.
MECHANIZM
Handler trzymany w useRef i nadpisywany efektem — subskrypcja widzi zawsze świeży callback bez
ponownego add/remove. Właściwa subskrypcja w drugim useEffect z cleanupem (B3). Typ zdarzenia
wyprowadzony z K extends keyof WindowEventMap.
KIEDY
Scroll, resize, keydown, beforeunload, online/offline, click-outside. Wszędzie, gdzie dziś piszesz parę
add/removeEventListener ręcznie.
GDZIE GO UŻYJESZ
Uogólnienie useBeforeUnload (A2) i sąsiad useIntersection (A3). A10: visibilitychange. Compound
components: click-outside.

TYPOWA FORMA
function useEventListener<K extends keyof WindowEventMap>(
  type: K,
  handler: (e: WindowEventMap[K]) => void,
  target: Window | HTMLElement = window,
  options?: AddEventListenerOptions
) {
  const saved = useRef(handler)
  useEffect(() => {
    saved.current = handler       // świeży callback bez re-subscribe
  }, [handler])
  useEffect(() => {
    const listener = (e: Event) => saved.current(e as WindowEventMap[K])
    target.addEventListener(type, listener, options)
    return () => target.removeEventListener(type, listener, options)
  }, [type, target, options])
}
PUŁAPKI
!  Ta sama referencja do add i remove — inline arrow w obu miejscach = nigdy nie odepniesz
 
!  useRef na handler — bez tego każdy nowy callback z rendera robi remove+add co klatkę
 
!  Typowanie z K extends keyof WindowEventMap — keydown dostaje KeyboardEvent, zero any
 
!  passive: true dla scroll/touch, gdy nie wołasz preventDefault — płynność scrolla
 
!  options w zależnościach jako stabilna referencja — obiekt inline tworzy nową co render
